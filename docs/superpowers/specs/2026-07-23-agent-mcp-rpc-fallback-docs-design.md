# Agent MCP and RPC Fallback Documentation Design

**Date:** 2026-07-23

## Context

Fundline exposes a public Streamable HTTP MCP server at `https://fundline.xyz/mcp`.
Production now has durable asynchronous MCP jobs enabled. A live activation probe confirmed
that an unpaid `run_workflow` call returns `awaiting_payment` with a `jobId`, `runId`, and
`recoveryToken` instead of falling back to the legacy synchronous x402 challenge.

The public documentation already mentions the MCP tools and durable flow, but it does not give
an agent enough copyable protocol detail to implement the full lifecycle safely. It also lists
only one Arc RPC endpoint. The Circle primary endpoint can return HTTP 429 or JSON-RPC error
`-32011` when its public request limit is reached, so an agent needs an explicit RPC rotation
policy that does not risk duplicate transactions.

## Goals

- Make the durable escrow-backed MCP lifecycle the primary documented integration path.
- Give an autonomous agent enough information to discover, quote, pay, enqueue, and recover a
  run without reading Fundline's source code.
- Keep legacy x402 documented as a compatibility path rather than the default for long jobs.
- Publish an ordered Arc Testnet RPC fallback list and precise failover rules.
- Prevent duplicate transaction submission when an RPC fails after accepting a raw transaction.
- Keep the human-facing `/docs` page and machine-readable `/llms.txt` guidance consistent.

## Non-goals

- No server-side multi-RPC implementation or automatic backend RPC rotation.
- No change to MCP tool schemas, job persistence, settlement, pricing, or smart contracts.
- No new public endpoint or standalone MCP client package.
- No publication of private environment variables, verification internals, lock design, API
  keys, treasury keys, payer keys, or other operational secrets.
- No webhook result delivery in this documentation change. Polling remains the recovery contract.

## Documentation Surfaces

### Human-facing documentation

Update the `Remote MCP server` section in `docs.html` so it includes:

1. MCP discovery and client configuration.
2. Tool roles for `list_workflows`, `run_workflow`, `get_run`, and `list_runs`.
3. A copyable durable run sequence with the exact fields passed between calls.
4. Recovery behavior after disconnects and timeouts.
5. A compatibility note for legacy x402.
6. A concise Arc RPC fallback policy and a safe JavaScript example.

Expand the existing `Network` section with the ordered RPC list and the fixed Arc Testnet
identifiers agents must validate before signing.

### Machine-readable documentation

Update the `/llms.txt` content generated by `handleLlmsTxt` in `server.js`. It will mirror the
same durable lifecycle, ordered RPC list, failover triggers, and duplicate-send protection in a
compact plain-text form suitable for autonomous agents.

The `/.well-known/mcp.json` manifest already points agents to `/mcp`, `/docs`, and `/llms.txt`.
Its schema and tool list do not need to change.

## Durable MCP Lifecycle

The docs will describe one logical paid workflow run as this sequence:

1. Call `list_workflows` and choose a valid slug and tier.
2. Call `run_workflow` without `payment`, using `paymentMode: "escrow"`.
3. Store the returned `jobId`, `runId`, and `recoveryToken` before sending funds.
4. Verify `chainId`, USDC address, escrow address, and exact six-decimal base-unit amount.
5. Approve only the quoted amount and call `fund(runId, amount)` from the payer wallet.
6. Call `run_workflow` again with `payment.jobId`, `payment.runId`, and
   `payment.recoveryToken`. Treat `queued` or `processing` as acceptance, not completion.
7. Poll `get_run` with the same `jobId` and `recoveryToken` until `succeeded`, `refunded`, or
   `failed`.
8. On disconnect or timeout, resume polling the existing job. Never create and fund a replacement
   job merely because the client lost its HTTP connection.

The recovery token is an authorization credential. Examples use placeholders, and the docs state
that it must not be logged, committed, or shared. Successful results remain retrievable for seven
days by default.

## x402 Compatibility

The docs distinguish two x402 behaviors so clients do not mix their credentials:

- A new MCP client may request `paymentMode: "x402"` on its first `run_workflow` call. The tool
  returns a durable `jobId`, `recoveryToken`, and exact x402 payment requirement. After payment, the
  client enqueues the same job with its job credentials, payer wallet, and transaction hash, then
  polls `get_run` normally.
- A legacy client may obtain an HTTP 402 challenge from `POST /api/workflows/:slug/run`, pay it,
  then call MCP `run_workflow` with only `payment.payerWallet` and `payment.txHash`. This preserves
  the synchronous compatibility path but does not provide a pre-payment durable recovery
  credential.

Escrow remains the recommended path because its refund behavior is contract-backed. Quoted async
x402 is useful when a client needs durable result recovery but cannot fund the escrow contract.

## Arc RPC Rotation

The suggested client order is:

1. `https://rpc.drpc.testnet.arc.network`
2. `https://rpc.blockdaemon.testnet.arc.network`
3. `https://rpc.quicknode.testnet.arc.network`
4. `https://rpc.testnet.arc.network`

Agents rotate to the next endpoint only for transport or provider availability failures:

- Connection failure or request timeout.
- HTTP 429.
- HTTP 5xx.
- JSON-RPC error `-32011`, including `request limit reached`.

Agents do not rotate and blindly retry for semantic or deterministic failures:

- Wrong chain ID.
- Contract revert.
- Insufficient funds.
- Invalid nonce, signature, address, amount, or request parameters.
- A Fundline API or MCP application error.

Every candidate RPC must return Arc Testnet chain ID `5042002` (`0x4cef52`) before it can be used
for signing or broadcasting. USDC contract calls use
`0x3600000000000000000000000000000000000000` and six decimals. Native gas accounting uses 18
decimals and must not be mixed with ERC-20 USDC amounts.

## Duplicate-send Protection

Read-only calls may be retried across RPCs with bounded exponential backoff and jitter. Transaction
broadcasts require a stricter rule:

1. Sign the transaction once and retain its serialized raw transaction and deterministic hash.
2. Submit that same raw transaction.
3. If the response is ambiguous, query the transaction hash and receipt through another healthy
   RPC before broadcasting again.
4. If the transaction is known or pending, continue receipt polling and do not replace it.
5. If it is absent after bounded checks, rebroadcast the identical raw transaction. Do not create a
   newly signed payment with a different nonce.

This rule protects agents from paying twice when an RPC accepts a transaction but drops the HTTP
response.

## Error and Recovery Guidance

- Preserve `jobId` and `recoveryToken` before on-chain funding.
- Treat MCP `queued`, `processing`, `settling`, and `refunding` as non-terminal states.
- Honor `retryAfterSeconds` when present and otherwise use a short bounded polling interval.
- If `get_run` is temporarily unavailable, retry the same job rather than paying again.
- If the run is refunded, verify the refund transaction on Arcscan.
- If every RPC is unavailable, stop and retry later. Do not switch chains or substitute a bridged
  USDC asset.

## Public Examples

Examples will use placeholder wallets, hashes, recovery tokens, and contract values. They will not
include a private key or expose Fundline's server environment. The JavaScript RPC example will show
the decision logic without becoming a complete wallet implementation.

## Rollout

The change is documentation-only. Push to `main` to deploy `docs.html` and the updated `server.js`
through the existing cPanel FTP workflow and Passenger restart. After deployment:

1. Confirm `/docs` contains the new durable MCP and RPC fallback guidance.
2. Confirm `/llms.txt` contains the same operational rules.
3. Call MCP `run_workflow` without payment and verify it still returns `awaiting_payment` with job
   and recovery credentials.

Rollback is a normal revert of the documentation commit. It does not require changing the durable
MCP production flag.
