# MCP Deliverable Artifacts Design

## Objective

Make every file generated by a Fundline workflow unmistakable to an MCP agent as a deliverable that must be downloaded and provided to the requesting user. The contract must work for PDF files today and arbitrary file formats in future workflows.

## Current Problem

Workflow responses can contain a persisted file capability in `file`, but the MCP adapter currently puts only the Markdown report into the visible `content` array. Although the file metadata can remain in `structuredContent`, clients and agents that primarily inspect MCP content can miss it and return only the Markdown report.

## Chosen Approach

Use three compatible representations for every generated file:

1. Add a normalized machine-readable entry to `structuredContent.result.artifacts` for asynchronous results, or `structuredContent.artifacts` for synchronous results.
2. Add an MCP `resource_link` content block for each artifact.
3. Append a plain-text deliverable section with an explicit instruction to download every file and provide it to the requesting user.

This follows the MCP tool-result model while retaining a text fallback for clients that do not render resource links or structured content.

## Artifact Contract

Each normalized artifact has this shape:

```json
{
  "kind": "file",
  "role": "deliverable",
  "filename": "proposal.pdf",
  "format": "pdf",
  "mimeType": "application/pdf",
  "url": "https://fundline.xyz/d/example",
  "deliveryInstruction": "Download this file and provide it to the requesting user."
}
```

Required fields are `kind`, `role`, `filename`, `mimeType`, `url`, and `deliveryInstruction`. `format` is retained when supplied by the workflow. The adapter derives a MIME type from a small, explicit format map when the source object does not provide one. Unknown formats use `application/octet-stream`.

The existing `file` field remains unchanged for backwards compatibility. The MCP adapter derives `artifacts` from both the existing singular `file` object and a future `artifacts` array, removing duplicate URLs.

## MCP Content Contract

For a completed result with artifacts, the first content block remains text and contains the workflow report followed by a section such as:

```text
Deliverable files:
- proposal.pdf (application/pdf): https://fundline.xyz/d/example
Action required: Download each file and provide it to the requesting user.
```

Each artifact also produces a resource link:

```json
{
  "type": "resource_link",
  "uri": "https://fundline.xyz/d/example",
  "name": "proposal.pdf",
  "title": "Generated deliverable: proposal.pdf",
  "description": "Generated file deliverable. Download it and provide it to the requesting user.",
  "mimeType": "application/pdf",
  "annotations": {
    "audience": ["assistant", "user"],
    "priority": 1
  }
}
```

The explicit `role`, instruction text, MIME type, and resource-link block allow an agent to distinguish the actual file deliverable from the Markdown summary.

## Data Flow

The MCP adapter normalizes artifacts only after a successful backend response:

- Synchronous `run_workflow`: read `payload.file` and `payload.artifacts`, then expose normalized artifacts at `payload.artifacts`.
- Asynchronous `get_run`: read `payload.result.file` and `payload.result.artifacts`, then expose normalized artifacts at `payload.result.artifacts`.
- Accepted, queued, payment-required, failed, and artifact-free results retain their current behavior.

The backend workflow and document store remain responsible for generating and persisting files. This change does not embed binary data in MCP responses and does not change the capability URL lifetime.

## Error Handling

- Ignore malformed artifact candidates that do not contain a usable HTTP or HTTPS URL.
- Use a safe fallback filename such as `workflow-deliverable` when a valid file has no filename.
- Use `application/octet-stream` when the MIME type cannot be determined.
- Do not claim that a file exists when persistence returned `null` or no valid artifact was supplied.
- Preserve the existing Markdown or status response when no valid artifact is available.

## Testing

Tests will cover:

- A synchronous `run_workflow` response with a legacy singular PDF `file`.
- An asynchronous `get_run` response with a legacy singular PDF `file`.
- Multiple future artifacts with different MIME types.
- Machine-readable `role: "deliverable"` and `deliveryInstruction` fields.
- One `resource_link` per valid artifact with filename, MIME type, URI, and audience annotations.
- Visible text that explicitly tells the agent to download and provide each file to the requesting user.
- Backwards compatibility for existing `file` fields and artifact-free responses.
- Deduplication and rejection of malformed artifact entries.

## Non-Goals

- Changing workflow generation, document rendering, or file persistence.
- Embedding file bytes directly in the MCP tool result.
- Guaranteeing how every MCP host renders a resource link in its user interface.
- Changing the authorization or expiration policy of document capability URLs.
